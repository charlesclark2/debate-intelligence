# `domain_redirect` module

A domain that exists only to send people somewhere else: `wfbdebate.com` and
`www.wfbdebate.com` answer every request with a 301 to the same path on `wfbdebate.org`.
Spec: [`v1-e36-t02-site-hosting`](../../../plan_specs/v1/e36-team-website/t02-site-hosting.yaml).
Decision: [ADR-0012](../../../docs/adr/0012-web-hosting.md).
Operator steps: [docs/runbooks/team-website.md](../../../docs/runbooks/team-website.md).

Called from [`envs/prod`](../../envs/prod/) only; dev passes no redirect domains, so the module
is not instantiated there. It holds no account id, region or domain name — the names are inputs.

## Why a CloudFront Function and not a redirect bucket

The older recipe is an S3 bucket with `redirect_all_requests_to` behind a distribution. That
needs the **S3 website endpoint**, which is plain HTTP, has to be public, and cannot be
restricted to a distribution — three things the task spec forbids outright. A viewer-request
CloudFront Function does the same job with no bucket at all: nothing to make public, nothing to
leave objects in, and nothing to pay for beyond the requests.

The distribution still has to name an origin, even though nothing ever reaches it, because
CloudFront requires one. It names the real site over HTTPS, so that if the function were ever
removed the failure mode is serving the site from the wrong name rather than an error page.

## What it creates

| Resource | Notes |
|---|---|
| `aws_acm_certificate` (+ validation records and wait) | Its own certificate: these are a different registrable domain from the site's, so they cannot share one |
| `aws_cloudfront_function` | Returns `301` with `Location` and `Strict-Transport-Security`, preserving path and query string |
| `aws_cloudfront_distribution` | `redirect-to-https`, `TLSv1.2_2021`, caching disabled, **no logging** |
| `aws_route53_record` | Validation records and A/AAAA aliases — only when `route53_zone_id` is set |

HSTS is set inside the function rather than by a response headers policy, because a response
generated by a viewer-request function is the one case where it is simplest to be certain the
header is sent.

## Inputs

| Variable | Notes |
|---|---|
| `domain_names` | The names being redirected. The first is the certificate's common name |
| `target_host` | Where they go. A validation refuses a `target_host` that is also in `domain_names`, which would redirect forever |
| `route53_zone_id` | The **`.com`** zone, not the site's. Null means the operator adds the validation records at the registrar and the apply runs twice |
| `strict_transport_security` | The header value sent on the redirect |

## Tests

```bash
terraform -chdir=infrastructure/modules/domain_redirect init -backend=false
terraform -chdir=infrastructure/modules/domain_redirect test
```

Five runs with `mock_provider "aws"`: no credentials, no network. They assert the redirect is
permanent, keeps the path, carries HSTS, runs on viewer request, serves its own certificate over
TLS 1.2, writes its DNS records in the `.com` zone, and that no S3 website endpoint or public
bucket appears anywhere in the path.
