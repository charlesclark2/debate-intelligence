## Summary

`FileQualityService` (`debate_core.application.file_quality_service`) checks a built evidence file
before anyone reads from it. It trusts neither the file nor its sidecar:

* it reads `<file>.provenance.json` against its own schema, and checks it describes these bytes;
* it re-parses the built `.docx` through the `DebateFileParser` port;
* for each card it fetches the source by SHA-256 from the blob store, re-parses it, and finds the
  card at the recorded paragraphs;
* it runs eight checks and writes `<file>.quality.json` and `<file>.quality.md` beside the file.

The checks are pure functions of parsed values in `debate_core.evidence.file_checks`. Every digest is
recomputed from the two re-parses with t02's `text_sha256` and `formatting_sha256`. A failure is never
turned into a warning: only the cite rule (your ruling) and two other faithful-copy cases warn. There
is no CLI surface.

**The Goal is `Succeeded`.** Every criterion has a passing run below. ac2's timing is 0.14 s per 100
cards on this Mac.

**Read first:**

* **[Deviation 2](#deviations-from-the-spec):** a disclosure on record that names no round or no
  tournament is a WARN, not the FAIL ac4 lists. I read your note's "the disclosure (or none on

* **[The camp-card suppression decision](#decisions-and-assumptions)** (decision 7): a camp card is

## Decisions and assumptions

1. **A report's status is PASS or FAIL.** A warning never fails a file; each check's summary is
   PASS, WARN or FAIL. `files publish` (t05) gates on the status.
2. **A check that cannot run FAILs, saying why.** Without a valid sidecar nothing about a card is
   established, so identity, alignment, provenance and suppression FAIL as "not checked without a
   valid sidecar". The built file's own checks still run. A built file the parser refuses fails every
   check that reads it.
3. **Sidecar errors** are reported as each error's location and pydantic's message
   (`cards.1.source_sha256: Field required`), with `include_input=False`, so no value reaches a
   report.
4. **Headings.** A heading is out of place when the nearest level above it *that the file uses* is
   not open. Only that level is asked, so one misplaced block is reported once, not again for each tag
   under it. A file with no hats may put blocks straight in a pocket (t01's rule). "In profile style"
   means the exact style id's rule fired; an alias, a display name, `basedOn` or a heuristic is not.
   Analytics and the provenance line are not headings.
5. **What a report names.** A card is named by position and fingerprint (a 12-character prefix in the
   Markdown). A heading in a section path is named by its text only if the sidecar records it as a
   recipe heading, the coach's text, and otherwise as `hat at paragraph 6`. A message names fields
   and digest prefixes. A test scans both reports of a failing, suppressed file for the school, team
   code, tournament, round, disclosure path, cite authors and evidence words.
6. **The provenance line.** It must be an Undertag paragraph inside the card's range, after its last
   cite paragraph. Its form is checked as far as the sidecar can say without copying the writer:
   * a caselist line starts `[Disclosed: <caselist> <first snapshot>` and names `<school> <team code>`
     when they are on record;
   * a camp line starts `[OpenEv: ` and names the camp, year and title it has.

   The writer's own `provenance_line` is in an adapter this layer may not import, and re-implementing
   it would make the check a copy of what it checks.
7. **Camp cards and the suppression list.** A caselist card is flagged by a suppression of its whole
   source or of its own disclosure digest. A camp card records no disclosure, and its sidecar entry
   records no camp path. So a suppression of one camp path (`v1-e30-t14`) cannot be told apart from
   another path of the same bytes, and *any* path suppression of its source flags it, saying so.
   That errs towards flagging a removed card for a person to look at. Making it exact needs the camp
   path's digest in the sidecar (follow-up 4).
8. **Suppressions in force** are computed as `SuppressionState.from_entries` applies them, keeping
   the first request that suppressed each source or disclosure; a test compares the two. Path holds
   are not read: they stop *new* bytes at a path, and a built file cites bytes the list names.
9. **Report file names** follow the sidecar's: `nhi-politics.docx.quality.json` and `.quality.md`.
   `check_file(docx, sidecar)` returns the report without writing anything, for a caller holding
   bytes.
10. **The style profile** the headings are held to is the one the parser reads with. The service
    refuses a profile of another version at construction.
11. **No "inside a repository" guard in the service.** The reports go beside the built file, and
    where built files go is t03's to decide (follow-up 1). Every test writes to `tmp_path`, and no
    report is committed.
