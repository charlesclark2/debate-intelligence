## Summary

The YAML file recipe now exists end to end. `debate_core.domain.file_recipe` models it (schema
version 1): a pocket > hat > block > item tree whose cards are E31 exact fingerprints, typed exactly
as `CardFingerprint.exact_fingerprint`. `debate_core.application.file_recipes` loads it, reporting
every error with its YAML line and path; hashes it over canonical JSON; and resolves each card to one
occurrence. Resolution reads three ports, all exercised in memory: the parsed store's
`occurrences.jsonl`, the caselist records (for who disclosed it) and the removal suppression list.
The PM's suppression rule is in the spec as ac6 with its own error code, `SUPPRESSED_OCCURRENCE`,
shown failing first. `docs/data/file-recipe.schema.json` is generated by
`scripts/export_recipe_schema.py` and drift-checked by a test in CI's default selection.
`docs/guides/file-recipes.md` walks through the three synthetic examples, and a test fails if the
guide and the example files differ.

**Look at first:** the Deviations. The recipe has five fields beyond ac1's list, and the session
touched two areas outside `constraints.packages`: a version list beside `FINGERPRINT_VERSION`, and a
test under `tests/scripts`. I added both to the spec's package list, marked as pending your review.

How it got there:

* **D15 survived the first round.** Pydantic itself refuses a number or a datetime whose time
  isn't midnight, so my test values never reached the check. The check matters only for midnight
  values, so the test now uses those (`1789430400`, and a YAML datetime at midnight), and catches it.
* **The second round aimed at what the tests did not obviously read.** B01 (a merged key's line
  overwriting an explicit one), B02 (a syntax error's line off by one) and B03 (a non-mapping
  recipe's line) survived, because the tests asserted only paths or `line >= 11`. They now assert
  exact lines.
* **B05 was deleted rather than tested.** It mutated the resolver's fallback to a parent path's line
  when a path had none, and that fallback cannot be reached for a recipe loaded from text, so the
  code was removed (`21fdfae`).
* **Coverage found a real bug.** On the changed modules, `--cov-report=term-missing` showed the
  YAML reader's error path untested. The test written for it showed that a control character in a
  recipe raised `yaml.reader.ReaderError` instead of being reported, because PyYAML checks every
  character when the loader is built and that line sat outside the `try`. It is fixed in `834948b`
  and reported with its line.

The lines still uncovered are unreachable or defensive: the root path always has a line; caselist
occurrence rows always carry a disclosure; a merge key pointing at its own mapping; one branch of
the item-kind lookup.

## Deviations from the spec

1. **Recipe fields beyond ac1's list.** I added five, each optional or required as marked:
   * `fingerprint_version` (required): the PM's notes ask for fingerprints to be validated against
     E31's `fingerprint_version`, and a recipe outlives a version bump.
   * `status: draft | ready` (default `ready`): `v1-e33-t03` ac2 and ac3 expect `status: draft` in
     the format t01 owns.
   * `school`, `side` and `tournament` on a pin (optional): the same bytes disclosed by two teams
     are two occurrences, and a team code is unique only within a school.

   `round` is named `round`, as the spec names it.
2. **Outside `constraints.packages`.** I added `EXACT_FINGERPRINT_VERSIONS` to
   `debate_core/evidence/fingerprints.py` so that the recipe check imports E31's definition, as the
   PM's notes ask, rather than restating it. `fingerprints.py`'s own docstring says a consumer
   comparing exact fingerprints across versions "must check this list"; the constant is that list
   as data. The drift test lives in `tests/scripts/` beside the other script tests. I added both
   areas to the spec's `packages` with a comment marking them as pending your review, since
   CLAUDE.md asks for scope changes to go into the spec. Strike them if you would rather they lived

## Decisions and assumptions

1. **How the resolver asks the suppression list (PM request).** The occurrence store and the
   suppression port already allow the exact question the parse pipeline asks when it rebuilds
   `occurrences.jsonl` (`_live_disclosures` in `caselist_parse.py`). An `OccurrenceRecord` carries
   its `source_sha256` and its disclosure digest, and `SuppressionState.suppresses(sha256,
   disclosure=digest)` answers both scopes: a whole source, or a disclosure withdrawn from that
   caselist path. The resolver loads the state once per resolve through the existing
   `load_suppression_state(SuppressionList)` and asks per row.

   It asks even though a rebuilt store already leaves such rows out, because a suppression merged
   from another machine's copy can stop a row before this machine's next `caselist parse`. It does
   not consult path holds: they stop new bytes at import and never reach the occurrence table.
2. **A pin to a source suppressed as a whole is refused before the store is read.** After a rebuild
   the removed source has no row left, so without this check the pin would be a plain
   `PIN_MISMATCH`. A pin with no match whose source has a withdrawn disclosure gets `PIN_MISMATCH`,
   with a note that a withdrawn disclosure cannot be used. I can't be sure the pin named the
   withdrawn one, and the message names no one.
3. **A pin whose matching rows mix suppressed and live copies of one occurrence is refused.** This
   is the same team at two paths with one path withdrawn. Refusing is the conservative reading of
   "refused, not silently re-pointed".
4. **AUTO's total order** uses only fields of the stored row: `last_snapshot` descending, then
   `source_sha256`, `first_element_index` and `disclosure`, all ascending. The spec's two keys come
   first; the other two make the order total (the same card twice in one file; one file at two
   paths). Tests check it under five store orders.
5. **"Latest snapshot" means `last_snapshot`**, the latest week a manifest listed the disclosure. A
   pin's `snapshot` matches when it falls in `[snapshot, last_snapshot]`. The doc warns that a path
   may be missing from some weeks inside that span.
6. **Same attribution, one occurrence.** Rows whose disclosures agree on school, team code, side,
   tournament and round are one occurrence, as in `CardOccurrence.occurrence_key` (a `(1)`
   re-upload). A pin matching several takes the latest. Rows that differ are an ambiguous pin:
   `PIN_MISMATCH`, saying how many disclosures matched and which fields can narrow it, and naming
   none of them.
7. **An occurrence with no disclosure on record still resolves**, with `disclosure=None`. A pin
   that names a school, team, side, tournament or round cannot match such a row.
8. **Bounds on the coach's own text**: headings at most 200 characters, a tag override 600 and an
   analytic 2,000. That holds the forbidden item ("no field carries evidence text") against a
   pasted card. The tests show the maxima accepted and one more refused.
9. **`topic` and `position` are kebab-case ids, not yet checked against a taxonomy**: E32 t01 is
   Pending. **`side` excludes `UNKNOWN`**, because a file is built for one side.
10. **Canonical JSON** is the validated model dumped with sorted keys, no whitespace, ASCII escapes
    and no null fields, so that a later optional field does not change every existing hash.
11. **Every structural error is reported in one pass.** Cross-section rules (side for the format,
    hats everywhere or nowhere, a pocket with both or neither) read the input in pydantic wrap
    validators, and their errors join the field errors in one `ValidationError`. Otherwise they
    would wait until every field was fixed.
12. **YAML is read strictly.** `side: no` (a YAML boolean) and a quoted `"3"` element index are
    refused, not coerced. A hex value made only of digits arrives as a number, and the error says to
    quote it. `!!python` tags are refused by the safe loader. A key given twice is an error.
    Recipes are bounded at 1,000,000 bytes and 100,000 nodes after aliases, so an alias bomb is
    refused before anything is built from it.
13. **Personal data stays out of messages and `repr`s.** No error message repeats a value the
    recipe gave (a rejected value can be a team code; pydantic's team-code message quotes its
    input), and resolver messages never name a school, team, tournament, round or path. A pin's
    school, team code, tournament and round, and a `ResolvedCard`'s disclosure, are off `repr`.
14. **Camp (OpenEv) cards are not referenceable in schema version 1.** `caselist` and a pin's
    `caselist` are `CaselistSlug`, which `openev` is not. See the PM questions.
15. **The three examples are `ready`, not drafts**, because t03 builds them and refuses drafts
    without a flag. The guide explains `status: draft`. All fingerprints are SHA-256 of a
    `synthetic recipe fixture: <label>` string; the schools (`Maple Grove`, `Cedar Hollow`) and
    team codes (`QX`, `ZaLu`, `AB`) are the repository's existing fictional ones, and a test holds
    them to that set.
