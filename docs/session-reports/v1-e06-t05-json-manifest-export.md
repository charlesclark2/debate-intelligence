## Deviations from the spec

1. **ac3's offset half does not hold, and cannot without changing the domain.** "Altering ... one span
   offset makes verify exit 1 with TEXT_MISMATCH or SPAN_OUT_OF_RANGE". Measured on t02's VERIFIED
   card (envelope [212, 712), omission [320, 422), 398 characters, five spans):
   * A `CardSpan` offset past the end of `evidence_text` is refused by `Card._check_spans`, and any
     single envelope or omission offset breaks ADR-0018's length invariant. Verify reads a
     schema-valid entry that is not a `Card` as `CARD_INVALID` (v1-e03-t06's rule, the
     `mixed.json` case), so all four are **exit 1, CARD_INVALID**.
   * A `CardSpan` moved inside the evidence still **verifies** (exit 0). Underlining is markup, which
     the debater may change; verify checks the quotation.
   * TEXT_MISMATCH and SPAN_OUT_OF_RANGE need the quotation's whole location moved: envelope and
     omission by the same amount (two to four numbers). By one character → TEXT_MISMATCH; past the
     snapshot's end → SPAN_OUT_OF_RANGE. The verifier's other SPAN_OUT_OF_RANGE (a span outside the
     reconstructed evidence) cannot come from a manifest: `Card` holds spans inside `evidence_text`,
     and the length invariant makes that as long as the reconstruction.

   Every case is a test, written to what happens. Exit 1 holds for every tamper that changes the
   quotation. Question 1 proposes the wording; the Goal stays `InProgress` until the PM rules.
2. **Files outside `constraints.packages`.** `packages/debate_core/schemas` and the debate_cli verify

## Decisions and assumptions

1. **Where the snapshot references go.** A top-level `snapshots` list, one entry per snapshot, in id
   order. A key added to each card entry was the alternative, but entries are the domain `Card`
   exactly (`card.schema.json`, `extra="forbid"`), so that would have changed the card's schema. Cards
   cut from one snapshot share an entry.
2. **The rules version 2 adds**, in `CardManifest`: every card names a snapshot, no card id is listed
   twice, and `snapshots` lists exactly the named snapshots, once each, in id order. Version 1 keeps
   its old rules and refuses `snapshots`. The schema says only what JSON Schema can: `snapshots` is
   required when `manifest_version` is 2 or more and absent otherwise, has at least one entry, and
   each entry is exactly the seven fields. The `if` tests "an integer of 2 or more", not `const 2`. An
   invalid version such as 0 then falls to the `else` branch and adds no second violation.
3. **A card's own hash is not checked against its reference.** A card whose `normalized_text_hash` or
   `normalizer_version` differs from its snapshot's is exportable. Verify then reports it
   HASH_MISMATCH, which is the honest record. Refusing the export would hide a card verify can judge.
4. **Card order is the caller's**, and references are in id order. A renderer's document order (t04)
   is then the manifest's, which is the order verify reports positions in. "Stable" means the same
   input gives the same bytes; sorting by id would have broken that correspondence.
5. **What the exporter takes and refuses.** It takes `Card`s, as the PM's note says
   (`export_json(cards)`), and reads snapshot records through `ArticleRepository.get_snapshot`, once
   per snapshot. It refuses no cards, a card listed twice and a card that names no snapshot with
   `ExportRefused(DomainError)`, before any read. A missing record propagates as `NotFound`. It is not
   wired into the container (PM: no wiring beyond verify's).
6. **The byte form** (`serialize_manifest`): `sort_keys`, two-space indent, `ensure_ascii=False`,
   trailing newline, UTF-8. Every field is written, defaults included (PM: no promise to older builds;
   `test_export_json_writes_every_field_a_default_leaves_empty`).
7. **What v1-e03-t06's reader did with a version it does not know** (the PM asked; measured on this
   branch before any change). It never raised a raw validation error: everything went through
   `InvalidManifest`, exit 2. But it never said "newer" either. `manifest_version` 2 with version 1's
   keys gave `the manifest is invalid at $.manifest_version: must be 1`. Version 3 with one new key
   gave `the manifest is invalid at $: properties the schema does not allow: 'snapshots' (1 more
   violation(s))`, which names the key and not the version. The reader also returned a literal `1` as
   the report's version. That was correct while 1 was the only readable version, and wrong as soon
   as 2 was (the CLI red run shows a version-2 manifest reported as version 1).
8. **The fix.** A version above `MANIFEST_VERSION` is refused before the schema runs, so a newer
   build's fields cannot be blamed instead. It raises `NewerManifestVersion(InvalidManifest)`, so the
   CLI reports it as before (exit 2, `INVALID_MANIFEST`, nothing verified), with the problem
   `manifest_version 3 is newer than this build reads (1, 2); install a newer build of
   debate-research to verify it`. A boolean or a non-integer version still goes to the schema. The
   CLI's fixed hint ("The schema is ...card_manifest.v1.json") is unchanged, because CLI source is
   outside this task (Follow-up 2).
9. **Pins that changed, and why.** Three tests pinned version 2 as invalid ("must be 1"), and version
   2 is now valid. Two take version 0 → `must be one of 1, 2`. The third, a new case, takes version 2
   without references → `missing required 'snapshots'`. `test_the_manifest_schema_refers_to_the_card_
   schema_rather_than_restating_it` listed `snapshot_id` and `normalized_text_hash` as card fields
   that must not appear in the schema text, and a snapshot reference names both. They were replaced
   by fields only a card has (`generated_by`, `citation`, `owner_id`) beside the original three.
10. **One schema file for both versions, still named `card_manifest.v1.json`.** The spec's node output
    names it, the CLI's help and README name it, and a `v2` file beside it would be the second
    schema the forbidden list rules out. The constant's docstring now says it describes every
    readable version (question 3).
11. **The verify command's own fixtures stay at version 1.** `manifest_world.py` writes
    `all_verified.json`, `tampered.json` and `mixed.json` with version 1, and their byte-for-byte test
    is unchanged. `test_the_verify_commands_own_manifests_stay_at_version_1` pins them, so moving them
    to version 2 is a decision someone makes, not a regeneration.
12. **The prior-version fixture comes from history**, not from code. It is the last commit before
    t02 regenerated `all_verified.json` (`8bf6a3b^`), so it lacks `generated_by`,
    `authors_are_organizations` and `cleared_by_student`: a manifest a prior build actually wrote. It
    verifies against the verify scenario's data directory unchanged.
13. **ac4's metadata values.** The fake router reports region, profile and temperature as null. A
    router in front of it reports a fixed Bedrock route, so the test can expect real values. The
    values are invented and written by hand.
14. **The round trip's data directory** is t02's `CardWorld` (in-memory stores) with the one snapshot
    copied out: the record through `SqliteArticleRepository.save_snapshot`, and both blobs through
